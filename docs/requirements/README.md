## 维护方式

1. 对既有范围的澄清直接更新当前基线，并在 Git 提交和对应迭代记录中说明。
2. 尚未确认的想法不直接写成既定需求，应先放入迭代记录的“待决问题”。
3. 较大的新增能力可先建立独立提案；确认后合并进产品基线，避免形成相互冲突的多份总需求。
4. 已取消的规则应在变更记录中说明，不长期保留在当前基线正文里制造歧义。
5. 文件名保持稳定，版本历史交给 Git，不创建“最终版”“最新版 2”等副本。
