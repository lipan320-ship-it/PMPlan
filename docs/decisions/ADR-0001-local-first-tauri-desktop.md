# ADR-0001：采用本地优先的 Tauri 桌面应用

- 状态：Accepted
- 决策日期：2026-09-17
- 决策者：项目维护者
- 影响范围：产品形态、前端技术、本地持久化、构建与发布

## 背景

工作规划时间板面向个人规划，核心操作包括在日期时间线上新增、拖动和拉伸子任务，设置母任务依赖，以及导入、导出完整规划数据。

当前需求明确要求数据在本地处理，并暂不包含云端同步、多人协同、账号体系和服务端能力。产品还需要在断网时可靠启动、自动保存，并让用户能够通过普通文件完成备份和迁移。

## 决策

项目采用以下产品和技术形态：

1. 以 **Windows 优先的本地桌面应用** 作为首个正式产品形态。
2. 使用 **Tauri 2** 提供桌面窗口、应用生命周期、本地文件访问和安装包能力。
3. 使用 **React + TypeScript + Vite** 实现时间板界面与交互。
4. 使用 **SQLite** 作为应用内部的权威数据存储，通过事务完成自动保存。
5. 保留版本化 **JSON 导入与导出**，用于人工备份、迁移和数据交换；JSON 不是应用运行时的唯一持久化介质。
6. 字体、图标、样式和脚本全部随应用打包，正式版本不引用 CDN，也不要求本地或远程 Web 服务常驻。
7. 首个版本不建设登录、云数据库、同步服务或遥测服务。

## 理由

- 桌面应用具有明确的安装入口、数据目录和文件操作体验，更符合“本地工具”的用户认知。
- SQLite 比浏览器存储更适合作为需要持续自动保存的权威数据源，并便于后续增加结构迁移、备份和恢复。
- 时间板本身适合用 Web UI 实现，现有 HTML 原型的视觉与交互思路可以继续复用。
- Tauri 使用系统 WebView 承载前端，并通过权限配置限制前端能够访问的系统能力，足以覆盖当前文件与数据库需求。
- 同一套前端业务层仍可在未来评估输出 PWA，但这不是首个版本的交付目标。

## 备选方案

### 单文件 HTML

不采用。它适合设计演示，但不适合模块化开发、可靠持久化、数据库迁移、自动化测试和安装发布。

### PWA

暂不作为正式产品形态。PWA 可以离线缓存，但首次安装依赖 Web 来源，数据仍受浏览器站点存储与用户清理行为影响，文件操作体验也弱于桌面应用。

### Electron

暂不采用。Electron 的全 JavaScript 工具链成熟，但会随应用分发 Chromium 与 Node.js。当前产品边界较小，Tauri 更符合轻量本地工具的目标。如果未来出现依赖 Node.js 原生生态、系统 WebView 一致性不足或团队维护成本明显过高，可重新评估。

## 影响

### 正向影响

- 安装后可完全离线运行。
- 数据可稳定保存在应用本地目录，并通过 JSON 由用户自主备份。
- 可以使用原生打开、保存对话框和明确的应用生命周期。
- 前端交互仍使用成熟的 Web 开发生态。

### 成本与约束

- 构建环境需要 Node.js、Rust 和 Windows WebView2 相关工具链。
- 需要维护 Tauri 权限配置，文件系统权限遵循最小授权原则。
- SQLite schema 变更必须提供可重复执行的迁移。
- 发布时需要验证安装版、便携版、升级和数据目录兼容性。
- Windows 是首发平台；macOS、Linux 支持不能在未经测试时对外承诺。

## 实施约束

- UI 层不得直接拼接任意文件系统路径。
- 数据写入通过统一存储层完成，组件不得各自维护独立持久化方案。
- JSON 导入必须先完整校验，再以单个事务写入，失败时不得污染当前数据。
- 数据库文件、自动备份和用户导出的 JSON 必须定义清晰且互不混淆的职责。
- 正式构建必须在断网环境中完成启动与核心流程验收。
